# Local timing review — 2026-10-07

Scope: current production timing changes at `55e3300`: PIA handshake and `mod_other` exceptions in `Arcade-Exidy2.sdc`, plus audio-domain reset synchronization and `pause` use in `rtl/audio_board.v`. This is a source-level review with the Oct 7 full-flow STA outputs incorporated below.

## Findings

- **PIA exceptions match instantiated hierarchy names, but intentionally suppress the entire PIA-to-PIA/T65 sequential boundary.** Source hierarchy is `exidyAB:sound_board|pia6821:PIA_9B`, `PIA_8B`, and `T65:A6502`; 9B is clocked by `master_clock` (its neighboring comment says PH_1), while 8B and T65 use `audio_clk`. Both clocks originate in the same core PLL, so their actual phase/edge relationship must be reviewed with correct constraints before describing them as unrelated FPGA clocks. The two directional exceptions are scoped to these instances. Protocol edges and bus/control state (`ca1/cb1`, `ca2/cb2`, data/port registers) are sampled without synchronizers, so the exception removes timing analysis and does not prove safe capture. Firmware handshake and original-board behavior are the design rationale, but this still needs clock-path and game/audio validation.

- **Reset synchronizer implementation is a standard two-stage synchronous release/assert conditioner, with a reset assertion timing caveat.** `rst_meta` and `rst_sync` initialize to zero; both sample `reset_n` on `audio_clk`, and `rst_sync` drives all reset users identified in `audio_board.v` (T65, RIOT, PIA_8B, 6840, 8253, jt49 enable and filters). PIA_9B stays on raw `RESET_n`, as it is on the master side. The exception targets the first stage only. Because reset assertion is also synchronous, the audio logic may continue for up to two audio edges after raw reset asserts; this is consistent with the documented ~140 ns delay but should be checked against download/reset sequencing. The `rst_meta` exception target and hierarchy match the RTL instance name.

- **The `mod_other` exception has a plausible static-during-play rationale, but its endpoint scope is broader than the comment suggests.** Source is actual `emu|mod_other[*]`; destination `exidyAB:sound_board|*` covers the complete sound board, including master-clock PIA_9B and its generated/derived logic, rather than only audio-clock consumers. The actual `pcb[4]` use selects audio-board/filter source logic and its upstream `pcb` bus comes directly from `mod_other` in `Exidy2`. The pinned transport and this core RTL establish a useful contract: index selection precedes download, `mod_other` changes only on index-1 payload writes (`ioctl_wr`), those writes occur while `ioctl_download` is active, and raw core reset includes `ioctl_download`. Thus the byte is stable during ordinary gameplay. However, the SDC destination wildcard still spans all sound-board logic, and the source does not specify a minimum interval from download assertion to the first payload write; the audio reset synchronizer asserts only after destination edges. Narrow the exception to actual audio-clock consumers where practical, or retain the wider exception only with an explicit rationale. Check exception match/count in fresh TimeQuest output.

- **`pause` is a real remaining CDC candidate.** Top-level `pause_cpu` is registered by `pause` on the system clock and fans into `Exidy2` and then `audio_board`. The audio CPU's `.rdy(~pause)` samples this control on `audio_clk`; the mute input is combinational into `exidyAudioMix`. Neither path has synchronization or a timing exception in the current SDC, and `pause_cpu` can change while the audio clock is active. If fresh STA shows a setup path, inspect source and endpoint first; an audio-domain synchronizer for CPU ready and a registered/synchronized mute may address different needs and should not be treated as interchangeable. The user-visible pause behavior and audio transition need verification after any change.

## Download-contract evidence (Main MiSTer pinned tree)

The neighboring `../Main_MiSTer` checkout is at `d3e55f5` (2026-10-05). In `user_io.cpp`, `user_io_file_tx()` selects the file index first (`user_io_set_index(index)`, lines 2817ff), then starts the transfer with `user_io_set_download(1, ...)` (line 2828), sends file payload via `user_io_file_tx_data()` (e.g. lines 2917/2953/3001), and ends by calling `user_io_set_download(0)` (line 3032). The setters issue separate `FIO_FILE_INDEX` and `FIO_FILE_TX` SPI commands (`user_io_set_index()` and `user_io_set_download()`, lines 2114-2140). Thus the index selection itself precedes download-active, but payload writes occur within the active transfer interval.

In this core, `mod_other` is not assigned from the index command: `Arcade-Exidy2.sv` updates it only on `ioctl_wr && ioctl_index==1` (line 240). That means the register value is written by index-1 payload data, while `ioctl_download` is asserted. The same top-level makes raw core reset include `ioctl_download` (line 436). This supports the intended contract that configuration-byte updates happen during a ROM/download reset window, and that `mod_other` is stable during ordinary gameplay.

Limit: this software ordering and RTL gating do not prove that the audio-domain synchronized reset has already asserted at the exact first index-1 payload write. `RESET_n_au` asserts synchronously after up to two `audio_clk` edges; the transfer's separate SPI commands and normal file-transfer setup should allow time, but I did not find a formal minimum delay contract in these sources. Therefore describe the byte as stable during gameplay and written during the active download/reset interval; avoid claiming the audio domain is reset at every possible configuration write unless the interface timing or reset sequencing is separately guaranteed. The SDC still exempts all `sound_board` destinations, broader than the demonstrated audio-clock configuration consumers.

## 2026-10-07 Quartus map-stage note

The paragraphs below preserve observations made while fitting was underway. The final result is recorded above; the earlier pending status is historical.

The full-flow run has completed mapping and is in fitting; the preliminary log is `simulation/quartus-full-2026-10-07.log`. Its STA log emits Warning 332060 for several derived/gated clocks, including `audio_reset|rst_sync`, `auPH0`, `auPH0B`, and ripple/game clocks. `rst_sync` appears as a detected clock because the VHDL 6840 `ctrl_regs` process has an asynchronous `reset` in its sensitivity list and uses `if reset='1' ... elsif rising_edge(clock) ...`; Quartus also reports a generated latch clocked by that reset node. `rst_sync` is intended as a reset control, not a functional clock. This warning means timing coverage around reset-controlled logic and derived clocks needs review; do not infer complete timing coverage from the positive summary for only assigned clocks.

Mapping also reports Warning 13310 for the 6840 counter registers at `modules/6840/berzerk_sound_fx.vhd:199`: Quartus converts their asynchronous-reset registers to equivalent register-plus-latch circuits. The reset branch loads programmable `ptm6840_max*` values rather than a constant, which likely prevents mapping the reset behavior onto a dedicated constant-clear/preset pin. This is a synthesis implementation warning, not a timing pass/fail by itself; it deserves functional and hardware review, especially around reset and programmed counter values. Fitter/TimeQuest results are still pending, so this note makes no claim that the full run passed or that all crossings are covered.
