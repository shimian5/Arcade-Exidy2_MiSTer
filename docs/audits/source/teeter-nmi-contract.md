# Teeter Torture NMI contract

This source audit resolves Teeter's periodic interrupt and checks the NMI vector in the staged ROM set. It does not add Teeter support or change RTL.

## Finding

Pinned MAME 0.288 configures Teeter by inheriting the Venture machine, then calls `m_maincpu->set_periodic_int(FUNC(teetert_state::nmi_line_pulse), attotime::from_hz(10*60))`: one NMI pulse every 1/600 second (about 1.667 ms). The interrupt callback is part of the base 6502 device API. The pinned Teeter ROM set has a 64 KiB main CPU region with eight 4 KiB ROMs mapped from `$8000` through `$FFFF`. Reading the private staged archive in memory and applying that source-declared order gives NMI vector `$A21C`; the vector lands in the `11a-cpu` ROM. A direct `LDA $5101` occurs at `$A22F`, 19 bytes after the vector target. MAME maps `$5101` to `IN0` and connects Teeter's dial callback there. This is consistent with the NMI routine polling the dial, but this audit did not fully reconstruct branch/call reachability from `$A21C`; it does not claim a complete handler trace. No ROM bytes or disassembly are included here.

In this core, the main `T65` instance has `.nmi_n(1)`, so Teeter's NMI source is currently absent. The CPU runs from `master_clock` with `PH_1` as its enable and `~pause` as `rdy`. `PH_1` is asserted for one master-clock cycle every 64 master clocks. MAME's 11.289 MHz board clock divided by 16 gives 705,562.5 CPU cycles/s; the RTL's nominal 45.156 MHz master divided by 64 gives the same rate. At that nominal master frequency, 600 Hz is exactly 75,260 master ticks per event, so a simple integer master-clock counter is sufficient; no fractional accumulator is needed. The fitted master period is slightly different from the nominal value, so exact physical 600 Hz would require using the accepted fitted frequency when choosing the counter interval. A CPU-enable counter would need fractional intervals because 45.156 MHz / 64 / 600 = 1,175.9375.

## Candidate implementation contract

If Teeter is enabled in the future, generate the periodic request synchronously in the master-clock domain. A 75,260 tick counter gives 600 Hz at the nominal 45.156 MHz clock; adjust that interval only if the design requires 600 Hz relative to the fitted clock instead of the documented nominal board clock.

Keep NMI inactive while reset is asserted and clear the divider phase/request state on reset, avoiding an immediate event at release. The selected production T65 source is [`modules/cpu-t65/T65.vhd`](../../../modules/cpu-t65/T65.vhd). Its main process updates `NMI_n_o` and detects the active-low NMI edge only on rising `Clk` edges with `Enable='1'`; here `Enable` is `PH_1`, so pulses between enables are not seen. The edge detection is outside the `really_rdy` condition, and the comment explicitly says it detects NMI even if not ready. Therefore a pulse that is stretched until at least one `PH_1` sample is latched into `NMIAct` even while pause holds `rdy` low. Once ready resumes, the T65's normal request path can act on `NMIAct`. The implementation does not need a separate pause-pending latch, but it must stretch/align the 600 Hz event to a `PH_1` sample. A one-master-clock pulse is insufficient; hold low until a `PH_1`-enabled rising edge has sampled it, then deassert to re-arm the edge detector. A focused T65 fixture would be appropriate before integration to verify the exact resume behavior and no duplicate request.

## Evidence and limits

- Official pinned [MAME 0.288 `exidy.cpp`](https://github.com/mamedev/mame/blob/mame0288/src/mame/exidy/exidy.cpp): `teetert_state::teetert` sets the 600 Hz periodic NMI at lines 1514–1522; `exidy_map` maps `$5101` to `IN0` at lines 452–475; `teetert_input_r` implements the dial callback at lines 405–421; `ROM_START(teetert)` defines main CPU ROM mapping at lines 2197–2206.
- The local ignored archive `simulation/teeter-contract/roms/teetert.zip` is 24,439 bytes, SHA-256 `770B05AD8BD7C31A1FB0A5DA700CC6DCDA9EB26D815E0AD16A063EA37F66F61B`; its hash matches the read-only NAS source archive. The eight main ROM member SHA-1 values match the pinned MAME declarations. The vector and handler check was performed in memory; no extracted ROM files were created.
- Production references: `rtl/Exidy2.v` generates `PH_1` at the `$cencnt[5:0] == 31` compare and connects the main T65 with `enable(PH_1)`, `rdy(~pause)`, and `nmi_n(1)`.
- Selected CPU timing references: `modules/cpu-t65/T65.vhd`, main state machine near lines 674–718: enable gates state updates and input edge sampling; `really_rdy` gates instruction/interrupt request advancement, while NMI edge detection and `NMIAct` capture continue when `really_rdy='0'`.

The static vector/ROM inspection plus source map establishes the likely input-poll dependency, but it is not a complete CPU execution trace or hardware acceptance test. It does not validate a game boot with NMI enabled. A focused T65 fixture should verify pulse capture while paused, acceptance after resume, and one interrupt per edge before gameplay validation.
