# Side Trak production gap audit

Audit date: 2026-10-13. Source of truth for this audit is the pinned local MAME 0.288 `simulation/reference_sources/exidy.cpp`, checked against the current `rtl/Exidy2.v`, `rtl/rom_loader.sv`, the six released MRAs, and the retained MAME ROM availability manifest. This is a source audit; it is not a game-start or gameplay acceptance result.

## Findings

| Area | MAME definition | Current core consequence | Status |
|---|---|---|---|
| Profile | Side Trak is base Exidy (`sidetrac_map` calls `exidy_map`); fixed black/white profile is identified as `pcb[1:0]==00` in RTL. | Profile byte zero appears to select the intended legacy decode and B/W output. There is no Side Trak release MRA. | Candidate profile value is source-consistent; MRA/load not verified. |
| CPU ROM | Three 0x800-byte program ROMs at `$2800`, `$3000`, `$3800`; reset/vector shadow at `$ff00-$ffff` mirrors `maincpu+$3f00` (`exidy.cpp:508-516, 1820-1828`). | `eprom_0` can hold the 64KiB program image and the existing mirror/vector circuitry is shared. The MRA must place/fill the image at those offsets and duplicate the `$3f00` page at `$ff00`. | Exact source layout and hashes are known; runtime loading is untested. |
| Character generator | `sidetrac_map` maps `$4800-$4bff` ROM, and `draw_background` uses `maincpu+$4800` when no character RAM is present (`exidy.cpp:508-516, 1214-1268`). The ROM is `stl9c-1`, 0x400 bytes (CRC `08710a84`). | `CHARSEL` currently selects `$4800-$4fff` CSCG1 RAM for CPU reads/writes (`Exidy2.v:177, 253-254, 385-400`). The character serializer also reads `VRAM_out_CSCG1`, a dual-port RAM, rather than a profile-selected ROM source (`Exidy2.v:387-400, 545-550`). Thus Side Trak's immutable character ROM is not connected as MAME maps it. Needed: read-only 1bpp character-ROM fetch for the video path plus CPU reads from the program image at `$4800-$4bff`; do not allow writes to mutate the ROM profile. Define how the unused `$4c00-$4fff` page reads. | Confirmed production mismatch. Needs source-backed latency/serializer fixture before integration. |
| Sprite graphics | One 0x200-byte, 1bpp `gfx1` region (`stl11d`, CRC `3bd1acc1`); MAME `spritelayout` is 16x16, one bit per pixel (`exidy.cpp:1082-1100, 1826-1828`). | `eprom_1` is 2KiB and sprite addressing is 11 bits; this can contain the exact 512 bytes, but must verify bit/address sequencing and deterministic behavior for the unused upper 0x600 bytes. | Size fits; address/bit-order and blank-fill parity not tested for Side Trak. |
| Palette | Side Trak initialization sets the three color-latch bytes to R/G/B `{f8,dc,b8}` (`exidy.cpp:2546-2552`); MAME converts each indexed palette pen from those latch bits (`exidy.cpp:1168-1188`). This produces pens 0-7: black, white, black, yellow, white, white, green, black. | The RTL hardwires the `pcb[1:0]==00` palette to identical one-bit RGB channels (`Exidy2.v:704-722`), i.e. grayscale. The MAME palette is not all grayscale. This conflicts with the game's documented monochrome label and needs an intentional hardware-vs-MAME decision; don't silently replace one with the other. | Source discrepancy, not yet hardware resolved. |
| Inputs | `$5101` bits: start1/start2/right/left/button1/up/down/coin1, all active-low (`exidy.cpp:617-645`). DIP `$5100`: lives bits 0-1, coinage bits 2-3, top-score bit 4 (`exidy.cpp:617-633`). | Generic `ESR_GENERIC` bit order matches MAME (`Exidy2.v:145-150`); `DIPSWA` takes the low switch bits from `DIP1` (`Exidy2.v:150, 257`). Existing Targ DIP metadata is not Side Trak's map. | Control wiring appears compatible by bit order; candidate MRA needs explicit Side Trak DIP labels/defaults and direction/button metadata. Not gameplay-tested. |
| IRQ/status | MAME's `$5103` read returns the interrupt latch composed with `INTSOURCE`, preserving non-collision bits (`exidy.cpp:1143-1164`). A retained MAME 0.264 zero-input survey observed Side Trak `$5103=0x63` in all 3594 reads (`docs/reference_cases/int-latch-survey.json`). | RTL EIR currently packs vblank, coin lines, collision causes and hardwires bits 1:0 low (`Exidy2.v:743-766`). The survey's two low bits therefore differ from this RTL output. The survey used MAME 0.264 and attract-only input, so this is a regression target, not hardware proof. | Concrete source/capture mismatch to resolve in IRQ integration. |
| Audio | Side Trak maps writes at `$5200/$5201` to `spectar_audio_1_w/2_w`; machine uses four sample channels plus a 1-bit DAC and a 525kHz max tone frequency (`exidy.cpp:513-514, 1526-1557, 1736-1798`). It is marked imperfect sound. | The current shared `audio_board` models the legacy tone path for `pcb[4]==0`; there is no Side Trak-specific sample-trigger/DAC path identified in the current `Exidy2.v` / `audio_board.v` binding. | Confirmed model gap; exact sound parity is out of this bounded audit and remains open. |
| Memory map / sprites | Base Exidy map has 1KiB RAM at `$0000-$03ff`, mirrored video RAM `$4000-$47ff`, sprite registers `$5000/$5040/$5080/$50c0`, mirrored DIP/input/IRQ at `$5100/$5101/$5103`, color latch `$5210-$5212`, input `$5213` (`exidy.cpp:488-500`). Side Trak adds ROM `$0800-$3fff` and `$4800-$4fff` and sound writes `$5200/$5201` (`exidy.cpp:508-516`). | Current CPU decode broadly uses the common PROM-selected bus regions; exact Side Trak coverage of PROM decoder outputs, sprite-control lookup, register mirror aliases, and write qualification has not been run against a loaded Side Trak image. | Needs an actual map fixture after the profile decode is confirmed. |

## Exact source image material and MRA blocker

The pinned MAME definition and retained manifest agree on these five archive members: `stl8a-1` (0x800, CRC `e41750ff`), `stl7a-2` (0x800, `57fb28dc`), `stl6a-2` (0x800, `4226d469`), `stl9c-1` (0x400, `08710a84`), and `stl11d` (0x200, `3bd1acc1`). The manifest reports the 5513-byte `sidetrac` zip present on the supplied NAS and all five members good; it is not staged in `simulation/a2-local/roms` (only Venture, Pepper II, Mouse Trap and Hard Hat are staged). No archive bytes were copied or committed.

The source-backed base-CPU image can be assembled deterministically as: zeros `$0000-$27ff`; the three program files at `$2800/$3000/$3800`; zeros `$4000-$47ff`; `stl9c-1` at `$4800-$4bff`; zeros `$4c00-$ffff`; then copy `$3f00-$3fff` to `$ff00-$ffff` for MAME's vector shadow. The 0x200-byte `stl11d` sprite image fits at the start of the core's 0x800-byte sprite slot. This is a byte-layout proposal only.

## Bounded native reference capture

The NAS archive was staged to ignored `simulation/side_trak/roms/sidetrac.zip` and verified with the installed MAME 0.288: `romset sidetrac is good`. The 3600-frame run is reproducible with `tools/reference_cases/side_trak_reference.ps1` and `.lua`; exact inputs/frames and binary/source/ROM hashes are in ignored `simulation/side_trak/native-001/run-manifest.json`. No ROM bytes or screenshots were added to Git.

The Lua tap reports actual CPU transactions only and never reads `$5103` directly. It records 38,990 reads of `$5101`, all values `$ff/$7f/$fe/$fb/$ef/$f7/$bf`, matching idle, coin, start, right, button, up, and down active-low encodings. A real coin pulse at frames 60-69 changed `$5101` from `$ff` to `$7f`; the start pulse at 120-149 caused entry to the playfield by the frame-600 snapshot. Short direction/fire pulses were issued sequentially through frame 839; later snapshots show score progression to 1200 by frame 3600. `$5103` was read 3536 times and every real CPU read returned `$63`; the five `$5100` reads returned `$14` (2 lives, 1 coin/credit, top-score award enabled). These observations qualify startup/credit/start and basic control-input execution in MAME only, not controls on the MiSTer core or complete gameplay.

Across the full capture there were 7170 writes to `$5200` and 460 to `$5201`, confirming active use of the Side Trak-specific sound/control ports. The passive CPU read tap saw zero CPU reads in `$4800-$4bff`; this is expected for MAME's renderer, which reads character bytes directly from its region in `draw_background`, and must not be mistaken for evidence that the hardware character ROM is unused. The capture does not expose MAME's internal renderer memory accesses.

I did not create a loadable candidate MRA: the current `selector` reserves additional fixed slots for address-decode PROM (`$14800-$148ff`), video control (`$14900-$1491f`), and sprite control (`$14920-$1493f`) (`rtl/rom_loader.sv:30-42`), but pinned MAME declares no corresponding Side Trak PROM region or hashes. Filling those slots with another game's PROMs or zeroes would invent unsupported hardware data and could leave the production core nonfunctional. Once the decoder/control implementation is source- or board-backed, add a candidate MRA with the standard index-0 base image, profile byte `00`, and explicit Side Trak switch values; then validate the actual expanded byte stream with a source-image builder before trying the game.

1. Obtain the supplied Side Trak archive into ignored `simulation/` storage and verify each member against the above MAME CRC/SHA1 before constructing an image; no ROM data belongs in Git.
2. Specify and test character-ROM timing/bit order, CPU read values at `$4800-$4fff`, sprite slot upper-fill behavior, and base address decode/control PROM equivalents.
3. Resolve the MAME palette-vs-monochrome discrepancy and make the `$5103` low-bit/language source match an explicit source/hardware rule.
4. Add the Side Trak discrete sound triggers and 1-bit DAC path, or document a narrower supported audio model.
5. Compare the captured MAME startup/coin/start/play trace against an integrated core; this native reference alone does not establish MiSTer gameplay acceptance.
