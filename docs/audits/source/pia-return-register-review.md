# PIA return-data register review

Date: 2026-10-07. Scope: assess a proposed one-`master_clock` register on the eight-bit `audio_DO_bus` before it enters PIA_9B `pa_i`, with normal related-clock timing and no false path. This is a source-level safety review, not an implementation or proof of firmware behavior.

## Existing data and handshake path

In `rtl/audio_board.v`, audio-side PIA_8B is clocked by `audio_clk`; its PB output (`audio_DO_bus`) feeds main-side PIA_9B `pa_i`. PIA_8B CB2 is routed to PIA_9B CA1. PIA_9B CA2 returns to PIA_8B CB1. PIA_9B is clocked by `master_clock`, and its selected read data (`audio_data_out`) feeds the top-level `CPU_databus_in` register in `rtl/Exidy2.v`.

The selected PIA implementation is VHDL `modules/pia/pia6821.vhd`. PIA port-B data/DDR state changes on the rising edge of its local clock (`pia_write`); `pb_o` is a combinational function of that registered state (`portb_direction`). PIA input pins are selected combinationally in `pia_read`: when PA data mode is active, DDR bits configured as inputs return `pa_i`, while output bits return the PIA's own port data. Thus the path under review is genuinely a multi-bit input path into PIA_9B's read mux, not a request to synchronize a toggle/interrupt line.

The PIA's CA1/CB1 input and IRQ edge logic updates on the falling edge of its local clock. The CA2/CB2 handshake outputs use the PIA's control-register modes; for output handshake mode the associated port write clears the strobe, and the opposite-side control edge restores it. The output bus value changes from the PIA's registered data/DDR on the rising edge, while the CB2 output process acts on a rising edge using the prior `portb_write` value. That sequence gives the data a PIA-clock interval before the write strobe changes in the selected RTL. This is useful evidence for data-before-strobe ordering in that PIA model, but it does not establish how every game configures the PIAs or how long firmware holds the value.

The pinned MAME `exidysound.cpp` has a concrete related example in its Victory sound implementation: `delayed_command_w` writes the PIA port-A byte before asserting CA1 low; `response_r()` obtains the PIA B-port output before lowering CB1 to acknowledge the response. This models data-before-notification and response-through-read semantics. It is evidence for the intended PIA handshake shape, not a timing guarantee for every Exidy2 game/profile: the existing game captures are main-CPU traces and do not contain paired audio-CPU PIA writes/reads.

## Proposed register assessment

The fitted clocks are PLL-related: `master_clock` is output 0 at 45.153061 MHz (22.146 ns), and `audio_clk` is output 2 at 14.366883 MHz (69.604 ns), sharing the same PLL. The frequency ratio is 22:7 (period ratio 7:22), so the edge relationship repeats and should be analyzed as a related-clock path. The main T65 runs on `master_clock` with `enable(PH_1)`; `PH_1` is a one-cycle enable generated once every 64 master-clock ticks (about 0.7055 MHz). A one-master-edge register can therefore add at most one master cycle of data latency, while a typical main-CPU transaction spans many master edges.

Source-level judgement: a one-cycle register of the complete `audio_DO_bus` is a plausible timing repair and is materially safer than a false path or independent per-bit synchronizers. It preserves byte coherence by capturing all bits together, leaves the CA/CB handshake wires unchanged, and keeps the first crossing fully timed from `audio_clk` into `master_clock`. It may give the PIA_9B combinational read mux and top-level bus register another master cycle to settle before a T65 enabled sample. Since the byte is presented before the write strobe and is expected to remain available until read acknowledgement, the extra cycle is likely compatible with the intended handshake.

That conclusion is conditional, not guaranteed. The byte register does not itself prove metastability-free capture; the related-clock setup/hold path into the new flops must meet in TimeQuest. Nor does a one-cycle delay change handshake sequencing: PIA_9B's read-clear CA2 path can acknowledge during the active PA read, so a boundary case where a new byte arrives just as the main side starts reading could acknowledge before the staged bus has updated. The audio-side firmware's minimum data hold interval and earliest legal main read were not established from available captures or disassembly. The MAME example supports hold-through-ack intent, but it is not the exact evidence for every selected Exidy2 board configuration.

## Meaningful paired-clock fixture

Before accepting the added latency functionally, build a source-level fixture with the two production `pia6821` instances and a small driver/observer. Use the actual fitted PLL periods and phase relationship (master 22.146 ns, audio 69.604 ns, with the configured phase; sweep every distinct relative launch/capture phase rather than relying on one arbitrary offset). Configure PIA_8B for PB output and handshake strobe, PIA_9B for PA input/read handshake, and preserve the actual CA1/CB1/CA2/CB2 cross-wiring from `audio_board.v`.

Exercise consecutive bytes including `00`, `FF`, and bit-walking patterns. For each case, make the audio PIA write its PB data and trigger its normal strobe, then have the main side respond at the earliest allowed point and at later points. Check that the staged byte observed by PIA_9B and the top-level main-bus register is the complete intended byte before the first T65-enabled sample, that the data remains stable through the read/ack interval, and that neither side loses or duplicates the handshake. Include a deliberately invalid case that reads before the PIA handshake notification to document the protocol boundary. A fixture pass establishes RTL sequencing for tested phases and delays; it cannot prove electrical metastability resolution or actual game firmware timing.

The implementation should then be assessed with fresh full-flow TimeQuest results: confirm the new audio-to-master register path is timed and meets setup/hold, inspect the remaining cross-domain paths, and verify the full-flow fit actually includes the changed source. No production implementation was made in this review. A candidate register is conditional on fixture and full-flow evidence; false-path waivers and independent per-bit asynchronous synchronizers are not recommended.
