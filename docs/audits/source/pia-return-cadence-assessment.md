# PIA return-byte cadence and selective-capture assessment

This source-only review asks whether the current CPU enable cadence proves a safe selective return-byte capture point. It does not modify RTL or timing constraints.

## Source schedule

`rtl/Exidy2.v` increments `cencnt` every `master_clock` edge and registers `PH_1` when the prior low six count bits equal 31. That creates one T65 enable every 64 master edges. With the fitted 22.146 ns master period, the CPU enable interval is about 1.417 us. `rtl/audio_board.v` increments `cencnt_au` every `audio_clk` edge and registers `auPH0` on the prior low four count bits equaling zero, one T65 enable every 16 audio edges. At 69.604 ns, that interval is about 1.114 us.

Both PIAs run on every parent clock edge, not on `PH_1` or `auPH0`. The PIA chip selects and read/write inputs are combinational from each T65 address and RW outputs. The T65 sequential state advances only when `Enable` is high and `really_rdy` permits it, so its address/RW state ordinarily remains stable between CPU enables. Consequently a bus cycle can be presented to the clocked PIA for many parent-clock edges; the PIA write process repeats a write on every edge while `cs && !rw` remains true. It is incorrect to treat a PIA write as a one-cycle pulse at `PH_1`/`auPH0`.

The PIA8 PB data and DDR are registered on `audio_clk`; `audio_DO_bus` is the combinational DDR-masked PB output. The existing `audio_byte_stage` samples that bus on every audio edge. On an edge that changes PIA8 PB state, nonblocking update ordering means the stage still sees the previous output; it sees the new byte on a later audio edge. PIA8 CB2 notification is itself registered: in the configured “write PB clears, CA1 edge sets” mode, `portb_write` is set in the PIA write process and CB2 consumes the previous `portb_write` on a subsequent audio edge. Data-stage and CB2 notification therefore have closely coupled but distinct NBA/event timing; neither should be modeled as a same-edge combinational transfer.

On PIA9, `pa_i` feeds the combinational PA read mux. When the PA data register is selected, `CPU_databus_in` samples the PIA `data_out` on every master edge. The T65 consumes that registered input only at its `PH_1` enable; it therefore sees the prior `CPU_databus_in` value at the enable edge. If a new read address is issued at one PH1 edge, the address decode and PIA output have almost 64 master edges to settle before the next PH1 consumption. This establishes the wrapper bus pipeline for an initiated CPU read, but does not establish that a read begins after a new audio reply.

## Handshake and earliest-read limit

The audio PIA CB2 output feeds PIA9 CA1; PIA9 CA2 output feeds audio PIA CB1. PIA9 CA1 sampling and IRQ state are clocked in the main PIA, and PIA9 CA2 read-ack behavior is clocked on the falling edge of `master_clock`. However, PIA9 `irqa` and `irqb` are left unconnected in `audio_board.v`, while the main T65 IRQ input is driven by the separate `rCPU_IRQ` signal. No RTL path forces the main CPU to wait for a new PIA8 CB2 event before reading PA. The CPU may already be polling or have the PA address selected when the audio byte changes. Therefore the 64-edge CPU cadence cannot be used as a guaranteed post-notification setup window.

The available MAME timestamp comparison also does not establish a positive write-to-read hold interval; several sampled main PA reads preceded their paired apparent audio PB writes. MAME timing is not board-level timing proof, but it reinforces that an assumed firmware wait cannot justify a selective capture.

## Candidate choices and evidence needed

1. **Capture only while PIA9 PA is selected for read.** This may reduce unnecessary destination updates. It does not improve the register-to-register setup relationship: the same source FF can still launch immediately before the same destination edge, and TimeQuest must time the crossing at that edge. The PA mux would also observe the old registered byte on the first edge that captures a new one; the registered CPU bus could see the new value on the following master edge. Although a PH1 read initiated at that point has many cycles before T65 consumption, this does not cover a read already selected before the new byte arrives. Establishing correctness requires a source-derived earliest read/write/notification trace for every supported game and an actual-T65 paired test for reads already in flight.
2. **Update the source byte only on a chosen audio phase class.** The fitted PLL output counters give a 7:22 master/audio tick ratio. Launching only on a favorable audio phase class can increase a particular next-master-edge separation, but delays visibility by up to several audio periods and does not prevent an already selected PA read from observing the old reply. A phase-class implementation also needs verified startup/reset phase for the two RTL divider counters. Do not use it without an explicit handshake or firmware bound and fitted generated-clock waveform evidence.
3. **Add a request/acknowledge mailbox.** A held byte plus synchronized request/acknowledge can give the byte a stable settling interval, but it changes the PIA handshakes and response latency. It needs an explicit contract for when PIA9 CA2 acknowledges, when audio PIA CB2 may be released, resets on each side, pause behavior, and a bound proving the main CPU cannot consume the reply before the mailbox presents it. No such contract is established by current RTL alone.

None of these cadence arguments supports a multicycle exception or false path. The current full-byte crossing remains a single-cycle related-clock path unless an explicit protocol is designed, simulated against the actual PIAs/T65 and game firmware behavior, and then represented by accurate timing constraints. The most useful next evidence is a trace from the earliest main PA read address through `CPU_databus_in` and PH1, paired with audio PB/DDR writes and CB2/CA1/CA2 edges for each supported game; absent that, selective capture is not proven safe.

Sources inspected: `rtl/Exidy2.v` (counter generation, T65 enable/RDY, and prior-cycle `CPU_databus_in`), `rtl/audio_board.v` (audio counter, T65, PIA wiring, return register and read selection), `modules/cpu-t65/T65.vhd` (Enable/RDY-gated state advance), and `modules/pia/pia6821.vhd` (PIA register, read mux and handshake processes). Fitted periods and output-divider counts are recorded in [`pll-constraint-contract.md`](pll-constraint-contract.md); the 3.150 ns positive-edge setup relationship is in the archived fitted setup report.
