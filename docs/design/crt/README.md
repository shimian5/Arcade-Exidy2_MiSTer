# Exidy2 CRT transport candidate

This is a schedule and interface recommendation for a future implementation. It is not a production RTL change, a PLL fit result, or physical CRT acceptance. The arithmetic model is [`tools/crt_schedule/model.py`](../../../tools/crt_schedule/model.py), and its retained derived output is [results.json](results.json); reruns write to ignored `simulation/crt_schedule/results.json`. The input raster evidence is [the accepted raw-raster report](../../audits/raster/README.md) and [measurements](../../audits/raster/measurements.json).

## Timing contract

The source raster evidence measures 336 pixels by 280 lines, 256 by 256 active, with one pixel event every eight 45.153061 MHz configured master-clock periods. Its configured-rate frame cadence is 59.992906303146256 Hz. The destination candidate is 336 by 262, also 256 by 256 active, at the same nominal frame cadence. Thus destination pixel/transport frequency is `262/280 = 131/140` of source, or 5.281295527678571 MHz / 42.25036422142857 MHz using the rounded source PLL parameter. A destination line takes 376,320 model time units versus 352,128 source units; both complete frames take 98,595,840 units.

The model uses common integer time units: 131 units per source master clock and 140 per destination master clock. That makes the nominal ratio exact for arithmetic; it does not make two independent physical clocks phase-locked. A continuously free-running clock error eventually consumes the finite row window: at ±1 ppm the bounded model predicts a fault after 9 frames for a fast destination (underflow) and 53,912 frames for a slow destination (row reuse). The test is finite and represents constant ppm error, not PLL phase noise or a real measured clock. A hardware contract must fault/blank before invalid pixels are shown if the actual clock relationship exits the proven window.

The preferred clock candidate uses Exidy's existing `pll_0002` output 1 (`outclk_1`, declared 11.288265 MHz) as the reference for a separate output-only PLL. Candidate integer settings are native M128/N1/C32 and CRT M131/N1/C35. Their exact ratio is `(131/35)/(128/32)=131/140`, which matches `262/280`; nominal VCO rates are about 1444.898 and 1478.765 MHz. The generated source declares output 0 at 45.153061 MHz and output 1 at 11.288265 MHz; the rounded decimal values differ from an exact 4:1 ratio by 1 Hz. This means the exact transport-to-source ratio still depends on the actual original PLL counters, not the displayed rounded frequencies. If output 0 and output 1 are generated from one shared VCO with a true 4:1 counter ratio, the candidate has an exact rational relation to the native source, avoiding the independent-50MHz fractional rounding drift in the prior model. The old independent 50 MHz Q32 estimates remain in JSON as an explicitly unverified fallback.

Intel documents Cyclone V output frequency as `fIN × M/(N × C)` and gives a 600–1600 MHz VCO range for the target I7 grade ([clock multiply/divide](https://docs.altera.com/r/docs/683375/current/cyclone-v-device-handbook-volume-1-device-interfaces-and-integration/clock-multiplication-and-division?contentId=4GdHK6ecQ843rvJ0lbPiEw), [PLL specifications](https://docs.altera.com/r/docs/683801/current/cyclone-v-device-datasheet/pll-specifications?contentId=lv8n4oznllHTLjTThTMAQw)). Those datasheet bounds make the nominal VCO arithmetic plausible; they do not establish PLL IP legality or a fit. Intel's PLL-cascade guidance requires a low-bandwidth upstream PLL and high-bandwidth downstream PLL, while the existing generated PLL QIP says bandwidth preset AUTO. Confirm its realized bandwidth, that `outclk_1` can route as the downstream `refclk` through an allowed clock network/placement, that output reconfiguration remains legal, and that lock/jitter meet the transport contract ([PLL-to-PLL cascading guidance](https://docs.altera.com/r/docs/683359/17.0/altera-phase-locked-loop-altera-pll-ip-core-user-guide/pll-to-pll-cascading), [Cyclone V PLL cascade specifications](https://docs.altera.com/r/docs/683801/current/cyclone-v-device-datasheet/pll-specifications?contentId=lv8n4oznllHTLjTThTMAQw)). This task did not invoke Quartus, inspect a fitter result, or measure silicon. Keep the game, audio, and native raster clock fixed; do not globally retune the original PLL.

## Capture, rows, and ownership

Capture source pixels on the actual pixel-enable rising event, not by sampling the BCLK level every master clock. `Arcade-Exidy2.sv` currently routes RGB through `arcade_video #(256,6)`, which repeats each one-bit RGB channel into a six-bit value and performs the existing sync/blanking and mixer pipeline. The conservative first candidate taps the final 24-bit RGB plus active/line/frame markers after the existing video path, so existing palette, gamma, and mixer behavior is retained. This costs 32 × 256 × 24 = 196,608 bits for a 32-row ring. RGB6 would cost 49,152 bits and raw 3-bit channels 24,576 bits, but either earlier tap requires proof that palette/mixer semantics and future color behavior are preserved.

Do not infer display row 0 from raw `vscnt == 0`. In the measured raw raster, the stable frame-origin transition occurs 313 pixels after a line wrap and active row 0 starts 23 raw pixels later. `arcade_video` line-latches vertical state on horizontal edges, and later video/mixer latency changes the RGB-valid coordinates. The integration fixture must observe the actual post-tap active row 0 and verify orientation, all 256 complete rows, and every pixel before this offset is used as an interface constant. A common fixed capture latency translates both schedules and cancels from the ownership margin, but the fixture still needs the real coordinate contract.

The arithmetic candidate publishes a row after its final active pixel, reserves two source transport clocks for publication uncertainty, and includes two destination transport clocks of read pipeline. It varies an explicit 8–32 destination-clock startup aperture; the conservative first-output delay is 255 source pixels plus this aperture (45.369–45.937 μs at the configured source rate). The mathematical minimum is 18 rows under these assumptions; choose 32 rows (196,608 RGB24 bits) to provide margin. At the two aperture endpoints, modeled publication margin is 0.145–0.713 μs and earliest slot-reuse margin is about 898.6–899.2 μs. These margins depend on the stated pipeline assumptions and cease to apply if measured implementation latency exceeds them.

Treat publication and overwrite as separate conditions. Each row slot has an unambiguous source sequence/row identity and active bounds. The consumer may read a row only after its publication is visible and before its next writer reuse. The model's 17-row negative case demonstrates overwrite before the last read; a missing row 17 blocks exactly destination `(frame 0,row 17,pixel 0)` and faults/blank rather than substituting a different row. These are arithmetic/decision-model checks, not implemented CDC or RTL fault-injection tests.

A 16-bit monotonically advancing row sequence with Gray-coded CDC is a candidate handoff. Compare modular sequence distances, require ring capacity below 2^15, and constrain Gray-bus skew so only one transition can be observed per source update. The model crosses 65535→0 and checks one-bit Gray transitions, but this does not implement metastability protection. Synchronize reset release independently in each clock domain; do not reset dual-clock pixel memory. Use a stable mailbox/acknowledgment for frame requests and pass only synchronized control/status between clocks. Keep write ownership separate from read ownership.

On a missing/unpublished row, late row reuse, malformed frame, stopped source, PLL unlock, or mode change, blank and latch a transport fault before stale or unrelated RGB is emitted. Retire the outstanding frame request, reset local ownership through synchronized domain resets, and resume only after lock, two complete destination frame boundaries, and a newly observed complete source row 0. A source pause may hold a frame only if all row ownership remains valid; once a deadline is missed, blank instead of repeating a partially overwritten image. The schedule script checks constant ±1 and ±10,000 ppm drift to finite first-fault points, but not this recovery state machine.

## Destination raster and controls

The candidate destination geometry is 336 × 262 with active pixels x=0..255 and active rows y=0..255; the remaining six lines are blank. Use HSync x=272..303 (32 pixels), horizontal porches of 16 and 32 pixels, and VSync on row 258 for one line with vertical porches 2/1/3, following the Victory current final contract. Do not copy Victory raw source phase constants: its position helper assumes different native H/V origins. Normalize from the measured Exidy post-mixer stream, then apply sync-only position shifts downstream while keeping RGB, DE, and CE stable. Preserve the established H range −32..+31 pixels and V range −16..+15 lines as selectable sync positions; document that extreme positions can crop rows/columns in downstream DV visibility windows. CRT mode bypasses H-size and effects that require scandoubling; effect/scandoubler requests select Native mode.

Keep the framework-facing RGB, HS, VS, DE, CE_PIXEL, and CLK_VIDEO path standard. A post-`arcade_video` capture retains Exidy's existing in-core mixer result; retiming must not duplicate or silently bypass that mixer. Preserve existing OSD composition/priority, gamma, HDMI tap semantics, VGA output, and `VIDEO_ARX/VIDEO_ARY` metadata. DV1 must receive the destination pixel cadence/repetition consistently. Check ordinary HDMI, analog/VGA, DV, DV1, OSD visibility, RGB order, blanking, and exact image orientation in integration. Victory's documented full-range DV position limits include a visibility-window crop tradeoff; carry that limitation forward rather than claiming every offset preserves the full image.

Mode selection should blank outputs, reset transport ownership, configure the output-only PLL, wait for busy completion and lock, wait two complete output-frame boundaries, then unblank only after a valid committed row is available. A user reset retains the selected mode. Native mode uses the native output candidate and same transport path unless integration proves a safe bypass. Game and audio execution remain on the unchanged source clock during every transition. PLL loss returns to blank/reset recovery. No clock mux may drive the framework stream from an unrelated source without satisfying its clocking rules.

## Reuse and implementation gates

The current Victory implementation is useful as a GPL-3.0-or-later reference: its rolling 32-row RGB24 converter, Gray-coded row publication, frame-request mailbox, sync-only position adjustment, output-control sequencing, and output-only PLL pattern are relevant. Preserve its attribution and GPL notices in any copied or adapted RTL, and review license compatibility for the consuming project. Do not copy Victory's raw phase constants or assume its receiver/physical acceptance transfers to Exidy. Do not change the upstream `sys` framework as part of this candidate.

Before treating an implementation as accepted, integrate a source-derived fixture that checks the post-mixer row origin and image direction; compare every RGB pixel for all active rows; exercise missing/late rows, overwritten rows, source stop, reset, both mode directions, PLL loss/relock, position endpoints, OSD/gamma/effect policy, and native image/timing preservation. Verify the actual PLL fit and output clock relation through the repository's complete Quartus project flow, then perform owner-controlled HDMI/analog/CRT hardware acceptance. This schedule model alone establishes none of those results.

Native output is a separate integration gate: this CRT arithmetic model does not prove a second-clock Native bypass or Native rolling transport. Preserve the existing Native pulse widths, phases and images unless a tested replacement contract justifies a change. The CRT porch choices above do not automatically define Native geometry. A common-output-PLL design must prove Native row ownership and clock drift too; a source-clock bypass requires safe clock selection and transition sequencing.

## Reproduction

From PowerShell at the Exidy repository root:

```powershell
py -3 tools/crt_schedule/model.py
```

The script asserts equal nominal frame periods, six common pipeline-offset translations, both startup-delay endpoints, all 2,359,296 checked RGB pixel ownership events, the 18-row minimum, the 32-row chosen ring, missing-row blocking, undersized-ring overwrite failure, 16-bit Gray sequence wrap, and finite drift fault cases. It writes ignored `simulation/crt_schedule/results.json`; run it again to regenerate that file. It does not compile RTL or make a physical clock claim.
