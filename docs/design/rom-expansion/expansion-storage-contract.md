# Exidy ROM expansion storage contract

This is an implementation contract for adding the FAX/FAX2 question ROMs and Mouse Trap CVSD voice ROMs while preserving the existing six MRA downloads. It defines byte order, index ownership, address mapping, memory behavior, and known unresolved hardware parity questions. It does not establish boot or gameplay success.

## Evidence and source versions

The ROM byte expectations come from `docs/baseline/roms/availability-manifest.json` (MAME 0.288 metadata) and are verified against the split ZIP members by `tools/rom_expansion/audit_regions.py`. The available NAS collection is labelled MAME 0.257; archive bytes and the manifest's size/CRC/SHA1 are the ground truth for this audit, while a 0.257-versus-0.288 metadata comparison remains unavailable. The MRA library contains six established MRA files; their index-0 streams and selector behavior remain unchanged.

Banking and address maps were checked against MAME commit [`27a8d9e85b58058965907d1d8a7a92f8ed039348`](https://github.com/mamedev/mame/tree/27a8d9e85b58058965907d1d8a7a92f8ed039348). ## Download index and compatibility contract

Reserve index 5 for FAX/FAX2 question data, index 6 for Mouse Trap CVSD data, and index 7 for an expansion descriptor. Indices 1 and 2 currently carry core options, index 3 is the default hiscore configuration index, and index 4 is its dump/NVRAM index. Keep index 0 exactly as-is: existing MRA byte streams, offsets, selectors, and the six current sets must not change. The index assignments are recorded in `region-budget.json` and `contract.py`.

The index-1 PCB byte carries hardware flags, not MAME's game enumeration: current examples include Targ `$01`, Spectar `$02`, Mouse Trap/Venture `$10`, and Pepper II/Hard Hat `$30`. There is no FAX/FAX2 MRA in the current six-file library. The FAX/FAX2 MRA variants will need a descriptor because their shared hardware profile does not distinguish which question banks are populated. Use bit 7 of index-1 as a new extended-protocol marker while preserving the lower hardware bits; the current source does not consume bit 7, but validate proposed values per profile before implementation. Place index 1 first in each expanded MRA, then send the descriptor on index 7 before index 0 and any index-5/6 payload. The descriptor is required only after the index-1 marker selects the extended protocol. Recommended fixed 16-byte record: ASCII `EX`, version byte `1`, profile byte (`1=FAX`, `2=FAX2`, `3=Mouse Trap CVSD`), required-stream bitmask byte (bit 0=index 0 base ROM, bit 1=index 5 questions, bit 2=index 6 CVSD), then index-0, index-5, and index-6 expected lengths as unsigned 24-bit little-endian byte counts, followed by two reserved zero bytes. Every extended profile requires a complete index-0 base ROM stream. FAX profiles require a 192-KiB index-5 stream, with banks 22/23 zero-filled; FAX2 requires a 192-KiB index-5 stream with all 24 banks. Mouse Trap requires a 16-KiB index-6 stream. Other expansion streams must have a zero length and a clear required bit. Index 5/6 data start at offset zero and contain bytes in MAME region-address order. This makes profile identity and lengths explicit without modifying index 0.

The core currently asserts reset for the duration of any `ioctl_download`, while only index 0 drives `dn_wr`. A fresh extended MRA must arrive in order index 1 marker, index 7 descriptor, index 0 base, then required index 5/6 streams. On index 1 with bit 7 set, clear descriptor validity, received-stream bits, and all per-stream byte counts before arming the new extended session. Keep that session active through the ordered transfers, and do not clear its received state at each `ioctl_download` falling edge. Hold machine reset until the descriptor is valid and every required stream (including base index 0) has received exactly its declared byte count. Reject invalid profile/mask/length combinations, duplicate/gapped/reordered addresses, or overlong transfers and keep reset asserted. The local MiSTer loader at commit `d3e55f51fa4f62343c79cacb4f2736269482c3b9` emits ROM entries in XML order (`support/arcade/mra_loader.cpp` lines 799–846); current legacy MRAs send index 0 before index 1. Therefore, after a completed expanded session, disarm its marker. If the next index-0 stream arrives without a fresh extended marker/descriptor, clear old expansion readiness and treat it as a new legacy session immediately; a following legacy index-1 transfer must leave it in legacy mode. Do not interpret a new legacy base using a stale descriptor. New expanded MRAs intentionally put index 1 first. This ordering is supported by the local loader, while installed MiSTer binary version remains a physical validation gate. Arbitrary transfer ordering is unsupported until the transport exposes a transaction/session identifier. Route indices 5/6/7 to separate memories/registers, count bytes per transfer, and validate the descriptor. Reset/download-done status crossing between HPS and CPU clocks must use synchronized control; bulk bytes cross through dual-clock RAM write ports, not unsynchronized sampled buses. When an expansion stream is absent, initialization policy must be explicit and deterministic; never expose stale bytes left by the prior set.

## Byte layout and address mapping

### FAX/FAX2 question store

Each question bank is exactly `$2000` bytes. The CPU window `$2000-$3fff` maps as `store[(bank << 13) | (cpu_address & $1fff)]`. MAME's bank select uses `data & $1f`; writes with upper bits set therefore alias the corresponding low-five-bit bank. Question source bank `b` begins at MAME `maincpu` region offset `$10000 + b*$2000`.

FAX contains banks 0–21. Its banks 22 and 23 are empty holes inside the declared `$40000` maincpu region; represent both as zero-filled slots in its fixed-length index-5 stream. FAX2 contains banks 0–23. Bank addresses 24–31 point beyond the declared MAME region for both sets. MAME's driver warns for selects above `$17`; those pointers do not establish a defined byte value. Recommended core behavior is to return `$00` for unpopulated/out-of-range banks and prevent stale memory from leaking, but this is a deterministic implementation choice, not confirmed MAME/hardware parity. Validate the observed fill behavior before claiming parity.

MAME also maps `$0400-$07ff` as an additional 1-KiB RAM area for FAX; this is mutable work memory, not ROM expansion storage. `$6000-$6fff` is character RAM in the source map. Confirm that profile-specific address decoding and existing character-memory capacity cover the full FAX window before implementation.

FAX also declares a `$0240`-byte `proms` region: `fxl-6b` at `$000` (256 bytes), `fxl-8b` at `$100` (32), `fxl-11b` at `$120` (32), and `fxl-12b` at `$140` (256). All four archive parts verify against the manifest; their individual hashes and the assembled zero-filled-region hash are in `region-budget.json` and `verified-rom-regions.json`. MAME comments that this region is loaded but not hooked up. The current core's PROM routing and effective widths do not establish byte-for-byte coverage of these four parts, including the additional `$100`-byte `fxl-12b`; classify this as an open hardware/profile-routing question, not an archive-byte mismatch. Before claiming complete FAX parity, determine which PROMs are electrically used, which can be omitted, and whether a separate download index/storage path is required. Existing 4-bit consumers must be compared after truncation against the physical mapped bytes.

### Mouse Trap CVSD store

The sound Z80 fetches a 16-KiB ROM window at `$0000-$3fff`, with address lines masked to 14 bits. Concatenate four 4-KiB parts in the declared MAME order:

| Store offset | ROM name | Meaning |
| --- | --- | --- |
| `$0000-$0fff` | `mta_2a.2a` | first bytes |
| `$1000-$1fff` | `mta_3a.3a` | second |
| `$2000-$2fff` | `mta_4a.4a` | third |
| `$3000-$3fff` | `mta_1a.1a` | final bytes |

The label `mta_1a` is the last address chunk, not the first. Sorting parts by filename or socket number would rotate the 16-KiB image and produce incorrect data. A legacy 14-bit loader path cannot append the full image after existing bytes without modulo-16-KiB wrap; use the dedicated index-6 store rather than relying on extension offsets. The sound device consumes the low data bit for its CVSD path, but retain all eight ROM bits in storage and preserve the Z80's ordinary byte reads.

## Storage and access timing

Provide independent storage so main CPU question reads do not contend with audio ROM traffic. The proposed logical payload is 192 KiB of question bytes (24 × 8 KiB, with FAX empty banks 22–23 explicitly initialized) plus 16 KiB of CVSD = 208 KiB. Do not infer exact BRAM cost from a flat `dpram_dc` with address width 18: that declaration allocates a 256-KiB byte memory. Use 24 explicit 8-KiB banks plus a 16-KiB CVSD memory, or report the rounded physical allocation. The current `eprom_6` is the audio-board 6502 program, not a CVSD Z80 ROM; `eprom_7` exists in `rom_loader.sv` but has no active consumer. `audio_board.v` instantiates the existing 6502 and audio program only. Therefore the new CVSD fetch port and CPU/sound-device integration are new work.

Recommended implementation is dedicated dual-clock on-chip RAM banks. The question store needs one byte-wide main-CPU read port plus the HPS/download write port; CVSD needs an independent sound-CPU read port plus its download write port. Where a target RAM primitive cannot supply the required independent ports, duplicate read-only contents into a second physical copy or arbitrate with explicit CPU wait states. Declare and verify read-during-write behavior; downloads occur under reset, so reads during matching writes should be ignored. Treat synchronous RAM read latency as at least one memory clock unless the selected primitive configuration proves otherwise. Align the read request to the CPU phase and supply valid data before the CPU samples it; otherwise add a wait-state or prefetch register. CVSD sound CPU and main CPU clocks may differ, so use a true dual-clock memory and synchronize reset/ready flags. Do not cross raw data or address buses through ordinary synchronizers.

The project QSF targets Cyclone V SE `5CSEBA6U23I7`; Intel's Cyclone V embedded-memory table lists 553 M10K blocks for A6 ([official capacity table](https://docs.altera.com/r/docs/683694/current/cyclone-v-device-overview/embedded-memory-capacity-in-cyclone-v-devices?contentId=aa2j1LcpVZmwQM5yFPck9Q)). At 8-bit × 1-KiB logical packing, the 208-KiB payload estimates to 208 M10K byte blocks; a flat 18-bit address declaration for questions plus CVSD would round to 272 such blocks. These are capacity models, not fitter results. Available free M10K capacity is unknown, and packing, port mode, existing logic, and other memories affect actual cost. The top-level MiSTer DDRAM request interface is present, while this top forces the board SDRAM pins to high impedance; no working external-memory request path was found in the active design. External DDRAM would require a designed request/fetch engine and CPU latency handling. Do not use a Quartus estimate as evidence until the complete project build has been run.

## Verification and remaining decisions

Run the model checks with `python -m unittest discover -s tools/rom_expansion -v`. Verify actual ZIP members without extracting them using:

```powershell
python tools/rom_expansion/audit_regions.py `
  --rom-dir '\\fairlanenas\data\Games\ROMS\MAME\MAME 0.257 ROMs (split)' `
  --output docs/design/rom-expansion/verified-rom-regions.json
```

The report contains actual size/CRC/SHA1 per archive member, MAME offsets, per-bank hashes, and assembled 192-KiB question / 16-KiB CVSD logical image hashes. Its assembly initializes holes to zero and does not write reconstructed ROM bytes to disk. It does not execute the ROMs or prove loader wiring. Before RTL work, settle profile/MRA generation, validate index-5/6 MRA transport on MiSTer, establish no boot gap across consecutive index transfers, confirm FAX/FAX2 empty/out-of-range read behavior against MAME or hardware, and verify the full FAX character-RAM decode. A later full Quartus flow is required to establish fit and timing; gameplay testing is separately required to claim boot or functional success.
